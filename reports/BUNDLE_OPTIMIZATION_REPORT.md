## 1. Executive Summary

This bundle audit analyzes the production artifact output generated by `pnpm exec vite build`. Vite transformed 3,041 modules and generated a highly partitioned chunk architecture. By segregating heavy third-party runtimes (Firebase SDK, KaTeX math typesetting, jsPDF export, Framer Motion animations) into isolated vendor chunks, DISHA 20-20 achieves fast initial page loads while deferring heavy analytical and administrative code until explicitly requested.

## 2. Manual Chunk Splitting Strategy

The Rollup output configuration in [vite.config.ts](file:///data/user/0/com.termux/files/home/Disha-/vite.config.ts#L274-L297) implements explicit vendor partitioning:

```ts
manualChunks: (id) => {
  if (id.includes('node_modules/react/') || id.includes('node_modules/react-dom/')) {
    return 'vendor-react';
  }
  if (id.includes('node_modules/firebase/')) {
    return 'vendor-firebase';
  }
  if (id.includes('node_modules/lucide-react/')) {
    return 'vendor-icons';
  }
  if (id.includes('node_modules/motion/') || id.includes('node_modules/framer-motion/')) {
    return 'vendor-motion';
  }
  if (id.includes('node_modules/katex/')) {
    return 'vendor-katex';
  }
  if (id.includes('node_modules/jspdf/') || id.includes('node_modules/html2canvas/')) {
    return 'vendor-pdf';
  }
}
```

### Benefits of this Partitioning
1. **Long-Term HTTP Caching**: Vendor libraries like `vendor-react` and `vendor-katex` have content hashes that remain immutable across application feature updates, achieving 100% cache hits on repeat visits.
2. **Parallel Resource Streaming**: Modern HTTP/2 and HTTP/3 multiplexing allows the browser to download vendor chunks in parallel streams without head-of-line blocking.
3. **On-Demand Isolation**: `vendor-pdf` (`176 kB` gzip) is never downloaded by students taking regular practice quizzes; it is fetched only when an admin or student taps *"Download PDF"*.

## 4. Ineffective Dynamic Import Findings & Analysis

During production compilation, Vite emitted 5 warnings regarding ineffective dynamic imports:

1. `src/utils/localDatabaseEngine.ts`
2. `src/utils/syncCoordinator.ts`
3. `src/utils/studentWriteBuffer.ts`
4. `src/utils/mcqSampleFormats.ts`
5. `src/utils/questionsStorage.ts`

### Root Cause
These utility modules were dynamically imported inside modals (e.g. `import("../utils/localDatabaseEngine")` in `ProgressContext.tsx` or `MCQSessionModal.tsx`), but were also statically imported in [src/App.tsx](file:///data/user/0/com.termux/files/home/Disha-/src/App.tsx#L46-L71) or [src/components/SyncStatusIndicator.tsx](file:///data/user/0/com.termux/files/home/Disha-/src/components/SyncStatusIndicator.tsx). When Rollup encounters both static and dynamic imports of the same module in the entry dependency graph, it promotes the module into the static entry chunk.

### Recommendation
Extract pure TypeScript types into `types.ts` and ensure utility singletons imported at the root level are either completely static or accessed through a unified service façade.
