# DISHA 20-20 — Disaster Recovery, Backup & Restore System Guide

## 1. Architectural Overview

The DISHA 20-20 Disaster Recovery subsystem (`src/server/backupEngine.ts`, `src/server/zipEngine.ts`, `src/server/typedSerialization.ts`) is an automated, zero-data-loss backup and restoration engine designed to protect all 56 Firestore collections, user subcollections, and media metadata.

### 1.1 Recovery Objectives
- **Recovery Time Objective (RTO):** $< 60$ seconds (Time to restore complete database from archive).
- **Recovery Point Objective (RPO):** $0$ seconds (Complete point-in-time snapshot with zero transactional loss).
- **Idempotency Guarantee:** Restoring the same backup multiple times produces zero duplicate documents or broken references.

---

## 2. Backup Archive Specification (.ZIP)

Every backup generated by DISHA 20-20 is compiled into a standalone, compressed `.zip` archive containing:

```
backup_2026-11-15T02-00-00.zip
├── manifest.json                             # Root metadata, collection counts, hashes
├── checksums.sha256                          # SHA-256 checksums for every file in archive
├── firestore/
│   ├── collections/
│   │   ├── subjects.json                     # Serialized documents for /subjects
│   │   ├── chapters.json                     # Serialized documents for /chapters
│   │   ├── topics.json                       # Serialized documents for /topics
│   │   ├── mcqs.json                         # Serialized documents for /mcqs
│   │   └── ... (56 root collections)
│   └── subcollections/
│       ├── users/
│       │   └── {userId}/
│       │       ├── progress.json             # Serialized /users/{id}/progress
│       │       └── history.json              # Serialized /users/{id}/history
│       └── articles/
│           └── {articleId}/
│               └── blocks.json               # Serialized /articles/{id}/blocks
└── storage/
    └── metadata.json                         # Cloud Storage file inventory & URLs
```

## 3. Reversible Firestore Type Serialization

Standard JSON cannot natively represent Firestore types (`Timestamp`, `GeoPoint`, `DocumentReference`, `Bytes`). To prevent type degradation during backup and restore, `typedSerialization.ts` encodes these types into reversible JSON envelopes:

### 3.1 Type Envelopes
- **Timestamp:**
  ```json
  {
    "__type": "Timestamp",
    "seconds": 1794700800,
    "nanoseconds": 500000000
  }
  ```
- **GeoPoint:**
  ```json
  {
    "__type": "GeoPoint",
    "latitude": 26.9124,
    "longitude": 75.7873
  }
  ```
- **DocumentReference:**
  ```json
  {
    "__type": "DocumentReference",
    "path": "subjects/rajasthan-history"
  }
  ```
- **Bytes / Blobs:**
  ```json
  {
    "__type": "Bytes",
    "base64": "SGVsbG8gV29ybGQ="
  }
  ```

Upon restoration, the engine deserializes these envelopes back into native Firestore classes (`admin.firestore.Timestamp`, etc.), guaranteeing 100% data fidelity.

## 4. The Five Supported Restore Strategies

When initiating a restoration, the administrator selects one of five strategies based on the operational scenario:

| Strategy | Mode Key | Operational Behavior | Use Case |
|:---|:---|:---|:---|
| **1. Merge / Upsert** | `MERGE_UPSERT` | Updates existing documents with backup values, creates missing documents, leaves existing non-conflicting documents untouched. | **Standard Recovery:** Restoring missing records without disrupting new user registrations. |
| **2. Clean Restore** | `CLEAN_RESTORE` | Overwrites target collections completely. Deletes any live documents that do not exist in the backup archive. | **Total Disaster Recovery:** Recovering from catastrophic data corruption or malicious tampering. |
| **3. Skip Existing** | `SKIP_EXISTING` | Only inserts documents that do not currently exist in the database. Never overwrites live data. | **Safe Migration:** Filling gaps without modifying active user progress. |
| **4. Dry Run / Validate**| `DRY_RUN` | Executes full zip extraction, parses every JSON file, validates schemas, verifies foreign keys, but issues **zero writes** to Firestore. | **Preflight Testing:** Verifying backup integrity before taking maintenance actions. |
| **5. Migration Restore** | `MIGRATION_RESTORE`| Cross-project restoration. Rewrites project IDs, strips obsolete admin claims, and restores foreign keys across different Firebase projects. | **Staging Setup:** Cloning production data to staging/testing environments. |

## 5. Disaster Recovery Step-by-Step Playbook

### Scenario: Accidental Deletion or Database Corruption

#### Step 1: Lock Database Mutations (Immediate Triage)
In catastrophic scenarios, activate the restore lock by creating the lock sentinel or enabling administrative maintenance mode to prevent incoming writes while the restore executes.

#### Step 2: Validate the Candidate Backup Archive
Submit the backup archive to the preflight validation endpoint:
```bash
curl -X POST https://disha-2020.vercel.app/api/admin/backup/upload-validate \
  -H "Authorization: Bearer <ADMIN_ID_TOKEN>" \
  -F "backupFile=@backup_2026-11-15.zip"
```
Ensure the response reports `"isValid": true` with `0` fatal errors and verified SHA-256 hashes.

#### Step 3: Execute Restoration
Trigger the restore job via REST API:
```bash
curl -X POST https://disha-2020.vercel.app/api/admin/backup/restore \
  -H "Authorization: Bearer <ADMIN_ID_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{
    "backupId": "backup_2026-11-15T02-00-00",
    "strategy": "MERGE_UPSERT"
  }'
```

#### Step 4: Monitor Job Progress
Poll the job status endpoint until completion:
```bash
curl https://disha-2020.vercel.app/api/admin/backup/jobs/job_rst_1731632400 \
  -H "Authorization: Bearer <ADMIN_ID_TOKEN>"
```
Expected final response:
```json
{
  "status": "completed",
  "progressPercent": 100,
  "phase": "Restoration Completed Successfully",
  "restoredDocuments": 18450,
  "failedDocuments": 0,
  "errors": []
}
```

#### Step 5: Post-Restore Verification
Run the automated integrity audit script:
```bash
pnpm run test:integrity
```
Verify that all 56 collections are hydrated, referential constraints are intact, and the application is fully operational.
