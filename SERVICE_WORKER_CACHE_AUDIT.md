## 1. Executive Summary

This audit evaluates the caching topology, Service Worker lifecycle, offline storage resilience, and deployment cache invalidation mechanics of DISHA 20-20.

The platform employs a multi-tiered caching architecture combining:
1. **Workbox Edge HTTP Precache & Runtime Cache** (Service Worker level),
2. **Persistent IndexedDB Storage** (`indexedDbCache.ts` and `localDatabaseEngine.ts`), and
3. **In-Memory Volatile Cache** for instant zero-latency UI rendering.

Automated verification tests (`tests/quiz-assets-sw-cache.test.ts`) passed with **100% success (4/4 tests)**, confirming flawless offline question access, version-keyed invalidation, and zero-data-loss buffering during network disruptions.

## 2. Service Worker Precache Configuration

The Service Worker (`dist/sw.js`) is automatically generated during build time with a complete manifest of immutable production assets:

* **Mode:** `generateSW`
* **Precache Entries:** 163 items
* **Total Precache Size:** 12,381.86 KiB (~12.1 MB)
* **Maximum Cacheable File Size:** 5,242,880 bytes (5 MB)
* **Glob Patterns:** `**/*.{js,css,html,ico,png,svg,woff,woff2}`
* **Navigation Fallback:** `/index.html` (serves client-side SPA routing shell offline)
* **Navigation Fallback Denylist:** Excludes `/^\/api\//`, `/^\/src\//`, `/^\/@vite\//`, and `/^\/node_modules\//`.

### Revision Hashing Mechanism:
* Vite chunks (`/assets/*-[hash].js`, `/assets/*-[hash].css`) have unique content hashes generated by Rollup in their filenames.
* Root static files (`index.html`, `icon.svg`, `sw-push-handler.js`, `manifest.webmanifest`) have cryptographic revision hashes computed by Workbox (e.g. `index.html` revision: `801de6b517775c55de63314de6598fbe`).
* **Guarantee:** When a new production release is deployed to Vercel, the Service Worker detects the revised manifest hashes immediately upon byte-level comparison of `sw.js`.

## 3. Workbox Runtime Caching Strategies

Nine distinct runtime caching rules are declared in `vite.config.ts`, each customized for the operational characteristics of the target resource:

| Route / Pattern | Handler Strategy | Cache Name | Max Entries | TTL / Expiration | Network Timeout |
|---|---|---|---|---|---|
| `/api/(quiz-assets/...)?.*v=` | `CacheFirst` | `static-quiz-data-cache` | 500 entries | 90 days | N/A (Instant) |
| `/api/quiz-assets/version` | `NetworkFirst` | `quiz-version-cache` | 10 entries | 7 days | 2 seconds |
| `https://fonts.googleapis.com/*` | `CacheFirst` | `google-fonts-cache` | 10 entries | 365 days | N/A |
| `https://fonts.gstatic.com/*` | `CacheFirst` | `gstatic-fonts-cache` | 10 entries | 365 days | N/A |
| `https://firebasestorage.../*` | `CacheFirst` | `firebase-storage-cache` | 200 entries | 90 days | N/A |
| `/assets/*`, `.(png\|svg\|webp)` | `CacheFirst` | `static-quiz-media-cache` | 200 entries | 90 days | N/A |
| Navigation (`mode: navigate`) | `NetworkFirst` | `pages-cache` | 50 entries | 30 days | Default |
| Core Routes (`/topics`, `/news`, etc.) | `StaleWhileRevalidate` | `core-routes-cache` | 100 entries | 30 days | N/A |
| Generic API (`/api/*`) | `NetworkFirst` | `api-content-cache` | 150 entries | 30 days | 3 seconds |

### Key Strategy Highlights:
* **Curriculum & Quiz Assets (`CacheFirst`):** Versioned curriculum bundles are keyed by immutable query parameters (`?v=...`). Once fetched, they are served entirely from cache, reducing Firebase read billing and providing sub-millisecond exam rendering.
* **Version Polling (`NetworkFirst`, 2s timeout):** The client checks for updated content versions via the network. If the device is offline or the connection stalls past 2 seconds, it seamlessly falls back to the locally cached version.
* **Core Application Tabs (`StaleWhileRevalidate`):** Student navigation across `/topics`, `/pyq_vault`, and `/live_tests` renders cached screens instantly while fetching fresh updates in the background.

## 4. Cache Invalidation & `SKIP_WAITING` Lifecycle

A common failure mode in poorly configured PWAs is "stale version lock," where users remain stuck on an old client bundle indefinitely. DISHA 20-20 implements an active, user-notified invalidation workflow:

### 1. Service Worker Message Listener (`sw.js`)
```javascript
self.addEventListener('message', event => {
  if (event.data && event.data.type === 'SKIP_WAITING') {
    self.skipWaiting();
  }
});
```

### 2. Client Invalidation Controller (`PWAUpdateToast.tsx`)
```typescript
const {
  needRefresh: [needRefresh, setNeedRefresh],
  updateServiceWorker,
} = useRegisterSW({
  onRegistered(r) {
    if (import.meta.env.DEV) {
      console.log('SW Registered:', r);
    }
  },
  onRegisterError(error) {
    console.warn('SW registration notice:', error);
  },
});
```

### 3. User Experience on Update:
* When a new version is deployed on Vercel, the browser fetches the updated `sw.js` in the background.
* Once the new worker finishes installation, `needRefresh` becomes `true`.
* An animated toast appears in the lower-right corner:
  > **Update Available**  
  > *A new version of DISHA 20-20 is ready.*  
  > `[ Reload ]` `[ ✕ ]`
* Tapping **Reload** calls `updateServiceWorker(true)`, dispatching `SKIP_WAITING` to the new worker, which immediately takes control of open tabs and refreshes the page with zero cache corruption.

## 5. Offline Data Tier & IndexedDB Resilience

Beyond HTTP caching, educational questions and test attempts require database-level persistence:

```text
┌────────────────────────────────────────────────────────┐
│                      Client Layer                      │
└──────────────────────────┬─────────────────────────────┘
                           │
       ┌───────────────────┴───────────────────┐
       ▼                                       ▼
┌───────────────────────────────┐   ┌───────────────────────────────┐
│     Workbox Service Worker    │   │   IndexedDB Database Engine   │
│  - Static JS/CSS/Fonts/Assets │   │  - Question Banks & Syllabi   │
│  - HTTP API Response Cache    │   │  - Student Attempt Outbox     │
│  - Offline Navigation Shell   │   │  - Unsynced Bookmark Mutations│
└───────────────────────────────┘   └───────────────┬───────────────┘
                                                    │
                                       ┌────────────┴───────────┐
                                       ▼                        ▼
                                ┌─────────────┐          ┌─────────────┐
                                │ Online Mode │          │ Offline Mode│
                                │ Direct Sync │          │ Queued Writes│
                                └─────────────┘          └─────────────┘
```

1. **Question Banks in IndexedDB (`src/utils/indexedDbCache.ts`):** Entire question sets for RAS, REET, and Patwar are cached locally. Students can practice hundreds of questions without internet connectivity.
2. **Outbox Buffer (`src/utils/studentWriteBuffer.ts`):** Student answers, bookmarks, and test submissions are written to local IndexedDB queues first.
3. **Automatic Resync on Network Reconnection:** When the browser emits the `window.online` event, `useFirebaseSync` flushes all buffered operations to Firestore without duplicate records or race conditions.
